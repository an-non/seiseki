# 長時間停止・承認待ち防止規程

- 文書版: 1.0
- 制定日: 2026-07-15
- 根拠: 同日のCodexローカルイベントログ診断

## 1. 診断結果

本日分のプロジェクト関連セッション3件を解析した。

- `require_escalated`を指定したcustom tool call: 11件。
- 最長の実ツール待機: 11分30秒。複合最終化処理の承認・実行待ち。
- ライブガード開始時の待機: 4分26秒。コマンド本体ではなく主に昇格承認待ち。
- 直近の停止要求: 昇格承認待ちのまま応答未完了となり、次の利用者入力まで5分49秒経過。
- 通常のCodexターン最長: 4分07秒。
- 5時間23分の最大無記録区間は`task_complete`後から次の入力までであり、実行中の処理ではない。

利用者が観測した約8時間の停止表示と、イベントログ上の実行時間は一致しない。ただし、承認待ち、UIの残留状態、VS Code再起動時の自動タスクが状態を不明瞭にしたことは確認できる。

## 2. 原因

1. サンドボックス外権限が不要なワークスペース内Node処理にも`require_escalated`を使用した。
2. `timeout_ms`はコマンド実行時間を制限しても、利用者の承認待ち時間を制限しない。
3. 複数操作を長い最終化コマンドへまとめ、途中状態と停止点を見えにくくした。
4. ライブガードを`folderOpen`で自動起動し、明示停止後にも再開しうる構成にした。
5. 「停止」要求に対し、即時停止より承認付き停止コマンドを優先した。

## 3. 必須回避パターン

### 停止語の優先

- 「止まって」「停止」「中断」「待って」を受けたら、新規の調査・編集・検証・承認要求を開始しない。
- 実行中の子処理がなければ、その場で停止を回答する。
- 本ワークスペースのガード停止は、明示済みの非昇格コマンドだけを使用する。承認待ちを発生させない。
- 停止できない処理がある場合、停止済みと偽らず、残存PIDと理由だけを報告してターンを終える。

### 権限昇格

- `sandbox_permissions: require_escalated`は、実際にサンドボックス拒否または外部システム変更が必要な場合だけ使う。
- ワークスペース内の読み書き、既存Nodeツール、状態確認、チェックポイント、検証、停止には使わない。
- プロジェクト規程上の説明・承認と、実行環境の権限昇格を混同しない。利用者が操作を明示依頼済みでも、OS権限が不要なら昇格しない。

### 時間上限

- 状態確認: 5秒を目標、コマンド上限10秒。
- 停止: 15秒を目標、コマンド上限20秒。
- 通常の単一検証: 原則30秒以内。
- 30秒を超える見込みがある処理は分割し、各段階の結果を先に返す。
- 一つのコマンドで停止、再起動、待機、再検証をまとめない。
- `exec`がセルを返した場合だけ`wait`を使用し、設定済みコマンド上限を超えて反復待機しない。

### バックグラウンド処理

- VS Codeのフォルダー起動を契機に自動開始しない。
- 利用者が同じターンで明示依頼した場合だけ開始する。
- ライブガードは最大2時間で最終同期後に自己停止する。
- 起動、状態確認、停止は別コマンドとし、結果を個別に確認する。

- 診断器: `session-archive/continuity/analyze-stalls.mjs`。
- 診断結果: `session-archive/continuity/vault/diagnostics/`へ時刻別に新規保存する。
- 原ログ、既存チェックポイント、監査ジャーナルは変更しない。
- 同様の停止が再発した場合、最初に本規程と直近診断を照合し、新しい長時間処理を開始しない。
